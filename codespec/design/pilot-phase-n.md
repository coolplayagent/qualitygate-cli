# 阶段 N：逐尝试执行时间归档与审计

> 日期：2026-09-17；需求：EVO-03、EVO-05；状态：工程设计，正式试点未启动。

## 问题与契约

阶段 K 按观察清单的 `elapsed_ms` 计算 30 分钟预算，阶段 J 按
`start_sequence` 审计封存顺序。两者都缺少独立归档的 harness 时间声明，
因此记录错误难以定位。阶段 N 对新计划启用 schema v9：

| 编号 | 可验收要求 |
|---|---|
| N-01 | 观察前计划仍封存原有预算、身份和顺序；v9 在每个尝试允许一份 `execution_evidence`，旧 v1–v8 拒绝此字段，旧计划的封存 JSON 和汇总语义不变。 |
| N-02 | 归档严格 JSON 包含 assignment ID、尝试号、开始/结束 Unix 毫秒、harness 摘要、状态、快照摘要和可空报告摘要。逐字段对应观察和封存计划；差值必须等于 `elapsed_ms`，时间须处于协议窗口且不晚于观察，同单元已归档尝试不得重叠。矛盾直接拒绝。 |
| N-03 | 每份归档文件采用受限相对路径、普通文件、SHA-256、精确字节和严格 JSON 内容；单份 64 KiB、总计 8 MiB。所有 CLI 输出前重读。缺记录可读入，但 `complete=false` 且最终接受主题不可生成。 |
| N-04 | `execution_audit` 列出每次尝试和缺失记录，按 `start_sequence` 对照已归档首次开始时间；相同或逆序为协议偏离，`protocol_ready=false`。缺失的首次记录保持未完成，不能推断顺序成立。 |

## 所有权和可信边界

`domain::pilot` 定义序列化契约、纯验证和审计；`config::pilot` 有界读取
归档文件；`application::pilot` 在封存、授权主题、汇总、最终主题前复核。
SHA-256 只绑定归档字节；harness 输出、时钟和外部进程事件仍是声明，
独立 reviewer 必须核对原始日志。v9 不把归档时间当可信时间戳。
