# 阶段 A：可比较基线的执行设计

> 状态：已落实为任务模板与 Rust 验证；观察参数、执行结果见试点记录
> 关联：[演进 SPEC 阶段 A](../requirements/agent-acceptance-evolution.md#5-实施阶段与试点输入)
> 方法：需求 → 执行设计 → 可复用任务资产 → 独立回归 → 实际基线记录 → 阶段验收

## 1. 本阶段交付

阶段 A 建立后续试点的可比较输入，不计算或宣称 Agent 提效收益。
复用现有 `check`、任务契约、报告与工具探测；不新增 Agent 调度器、审批服务或门禁计算逻辑。

2026-09-16 已确认的观察规模为 8 个任务（修复/重构各 4 个）、7 天；两模型 × 两流程
构成 32 个运行单元，每单元最多 3 次尝试/30 分钟，总上限为 96 次尝试/16 小时累计运行时间。
接受阈值保持原值，具体任务、负责人和其它执行输入的封存状态以试点记录为准。

## 2. 任务模板和执行方式

首批模板面向已有 `Cargo.toml`、锁文件和独立 `tests/regression.rs` 的 Rust 项目。
模板保留任务标识、可观察行为、必需命令与工具探测；使用者需审查具体测试是否覆盖自己的任务。
采用模板不能自动建立策略可信性，任务文件须通过团队既有流程进入选定策略提交。

缺陷修复基线运行相同的回归测试：旧实现应完成测试并暴露断言失败，修复后通过。
本阶段用实际两次 `check` 记录验证这种任务准备方式，不把它声明为自动的逐文件反例判定。
需要新增或修改测试文件的逐文件证明时，仍显式使用现有 `test_effectiveness` 契约和兼容生产者。

重构基线在改动前后运行相同的行为测试，允许两侧均通过。接口兼容性和额外回归按项目实际要求
加入契约；模板不能证明未声明的接口与行为等价。测试编译错误、零测试和执行超时都不能供给行为证据。

对实际案例固定 `base`、`head`、策略提交和任务路径，使用
`qualitygate check --diff <base>..<head> --task <task> --policy-ref <policy> --profile full --format json`。
尖括号值由试点确认记录和实际 Git 标识提供，不是可执行占位实现。
既有检查也可由 CLI 执行并留存原始生产者日志；不得将该分析器原本就能发现的问题归因于新增规则。

## 3. 基线记录与信任边界

每个案例记录类型（真实开发、历史回放或受控 fixture）、案例 ID、任务类型、源仓库、
base/head、策略提交、任务摘要、实际命令、工具版本、环境、时间与预算。
保留完整 JSON、原始日志和报告，使用摘要建立引用。初始失败和未完成记录不得被修复后的通过结果覆盖。

对照关系必须是相同案例和验证输入，不能把不相关提交上的两个通过结果配成重构基线。
实际 Agent 接入另外记录产品与 harness 版本、请求模型及服务商可提供的实际模型标识。
本地安装了一个可执行文件只证明工具存在，不证明凭据可用、任务已运行或实际模型版本已确认。

受控测试在临时 Git 仓库中运行真实 Rust 构建与断言，输出测试自己的基线证据。
这些证据明确标记为 fixture，只证明模板和记录链路，不能满足 A-01、真实 A-03 或模型实际调用观察。
报告与摘要不独立证明受信执行；真实试点仍由外部 harness 和复核者负责来源、预先确认及完整性。

用户已指定同一 Codex 的不同模型模拟两种 Agent；选用 `gpt-5.6-terra` 与 `gpt-5.6-luna`，
两组均使用 `medium` 推理强度。模型选择依据与实际可用性分开记录，服务端未提供实际模型证明时为未知。
`tests/pilot_codex_live.rs` 是显式启用的有费用接入探测：各一次、各 180 秒、每流最多 16 MiB，
调用既有 Rust runner；各自克隆固定提交，忽略用户配置和 rules，不复用会话，固定只读权限。
它要求实际执行 CLI 版本探测、读取本仓库契约并正确回答 `0/1/2` 和验收边界。
原始事件、回答、参数、用量与失败均保存。连接成功但工具执行失败时探测仍失败，不降级成通过。
该测试默认忽略，不在离线 CI 或覆盖率检查中自动调用模型；不得把未运行记录当作连接成功。
本机默认 bwrap 受限时允许显式选择当前 Codex 仍支持的只读 Landlock 后端，记录配置差异，
不自动切换。探测脚本的格式识别修正用离线正反例验证；归档重审检查有界文件、路径和摘要，
单独输出验证器摘要与原始判定，不覆盖原始索引。该索引是 harness 记录，不是新的 CLI 报告协议。

## 4. 验证与状态推进

- 先验证模板可被当前 `config::parse_task` 和 `Plan::build` 接受。
- 集成回归使用临时 Cargo 项目，验证缺陷修复旧失败/新通过、重构双侧通过、零测试拒绝和策略变更拒绝。
- 对每次结果检查任务身份、策略提交、代码快照、实际执行状态与日志摘要。
- 运行仓库必需格式、编译、Clippy、单元与集成、文档、覆盖率和完整 selfcheck；测试失败不得修改门禁来消除。
- 阶段状态从准备中到输入已确认，再到基线已采集、阶段验收完成。没有预先确认的输入，不能用准备测试成功跳过状态。
- 新增工程证据记录到需求映射；真实试点选择与结果记录在独立准备记录中。保持既有 M1–M4 状态与本阶段分别验收。
