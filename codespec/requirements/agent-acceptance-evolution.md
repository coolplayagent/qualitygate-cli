# 跨 Agent 验收能力演进需求 SPEC

> 文档版本：v1.3
> 状态：阶段 A–O 的工程契约已在本地实现；真实 8 任务、7 天试点及独立验收尚未启动
> 研究日期：2026-09-15
> 关联需求：[qualitygate-cli requirements §12](qualitygate-cli.md#12-跨-agent-验收能力演进)

## 1. 定位与成功标准

qualitygate-cli 面向工程团队提供跨模型、跨 Agent 的规范执行与任务验收层。
Agent 负责理解需求、提出规则和测试、修改代码；CLI 根据明确的策略、任务契约与执行证据计算门禁。
核心验收必须无需调用模型即可运行，模型自评、对话中的完成声明和本地报告摘要不能替代实际验证。

本轮演进的成功标准是：至少两种 Agent 在同一真实项目、可比较任务与资源预算下，
根据结构化诊断完成修复，并对最终快照执行完整验收；团队能够复查输入、策略、任务与证据，
测量相对既有流程的增量收益和执行资源；金额成本仅在有可靠计价时作为补充观察。
规则数量、支持模型数量和 fixture 通过数不单独构成产品收益。

本文同时记录已交付的阶段 A–O 工程能力及未完成的真实试点。[验收审计](../../docs/en/04-contributor-guide/03-requirements-to-test-evidence.md)
记录实现证据；[试点协议](../../docs/en/01-user-guide/05-real-repository-pilot.md)规定真实项目收益的独立验收。
本文不改变既有 M1–M4 的完成状态，不把文档检查成功或厂商评测结果计为试点通过。

## 2. 研究依据与产品推论

以下事实来自研究当日核验的官方资料。厂商能力描述、研究方法和本项目推论分别记录；
模型版本及可用性只作为有日期的背景，不成为 CLI 的兼容性要求或模型排名。

| 研究依据 | 来源所支持的事实 | 本项目推论 |
|---|---|---|
| OpenAI 模型文档 | GPT-6 Astra 面向复杂端到端工作，支持长上下文和编码、检索、shell 等工具能力 | 验收需描述跨文件、跨阶段任务，不能仅检查一段生成代码。[来源](https://developers.openai.com/api/docs/models/gpt-6-astra) |
| Anthropic 模型发布 | Opus 5 发布材料强调自主验证、根因分析和迭代效率，证据主要来自厂商评测与早期使用报告 | 应测量当前 Agent 自检之外的增量价值，不能假设已有规则长期有效。[来源](https://www.anthropic.com/news/claude-opus-5) |
| Google 模型目录 | Gemini 3.8 Flash 被列为面向长周期软件工程和自主 Agent 的稳定模型 | 将验证成本与交付质量同时纳入评估，支持不同成本层级的外部 Agent。[来源](https://ai.google.dev/gemini-api/docs/models) |
| Anthropic Agent 架构 | Managed Agents 将会话日志、执行循环和沙箱解耦，以支持恢复与长期执行 | CLI 复用外部执行框架，专注验收契约和可复查证据。[来源](https://www.anthropic.com/engineering/managed-agents) |
| OpenAI 改进闭环示例 | 轨迹、人工与模型反馈可转化为可重跑评测，再形成执行框架修改提案 | 真实失败应沉淀为候选规则和独立回归案例，并经过已有策略验证流程。[来源](https://developers.openai.com/cookbook/examples/agents_sdk/agent_improvement_loop) |
| Anthropic 评测方法 | 最终环境结果与 Agent 自述不同；程序、模型和人工评判各有边界，重复尝试的成功与稳定性应区分 | 验收以可观察结果为基础，保留失败尝试，模型意见作为待验证提案。[来源](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) |
| METR 研究方法 | 时间跨度以人类任务耗时衡量难度，不等于 Agent 连续可靠运行时间；研究任务与真实工作存在差异 | 不能将公开基准分数直接转换为项目交付成功率或收益承诺。[来源](https://metr.org/time-horizons/) |

既有工具已经覆盖部分需求：Promptfoo 提供多种 Coding Agent 的评测与轨迹检查，
LangSmith 提供评测和运行观察，GitHub 提供 PR 代码质量阈值。
本项目选择复用现有分析器和外部评测框架，重点建设任务验收、证据完整性与规则有效性，
避免重复统计既有工具收益。依据：[Promptfoo](https://www.promptfoo.dev/docs/guides/evaluate-coding-agents/)、
[LangSmith](https://docs.langchain.com/langsmith/evaluation)、
[GitHub](https://docs.github.com/en/code-security/how-tos/maintain-quality-code/set-pr-thresholds)。

## 3. 共用约束与接口边界

- 沿用 `check`、任务契约、策略选择和版本化 JSON 报告；新增输出视图或字段必须声明兼容性。
  本文不定义尚未实现的新命令、字段或 DSL 语法。已有配置不能因新增模板被隐式改变。
- 保持退出码 `0` 完整通过、`1` 阻塞违规、`2` 验证未完成。展示精简和诊断过滤不能改变门禁。
  缺失工具、零测试、超时、报告缺失与快照错配不能转成通过。
- `quick`、路径过滤和局部复验仅证明选定范围；最终交付需要最终快照上的全部必需检查。
  未提供任务契约时，只能描述仓库策略检查结果，不能据此宣称任务完成。
- 任务与策略的建立和修改由既有受信流程控制。固定 Git 引用或本地摘要本身不证明授权；
  CLI 不生成审批身份、签名密钥或可信 AI 作者标签。
- 默认对人工与 Agent 代码使用相同质量标准；AI 参与范围仅在团队明确要求并具备可信记录时启用。
- 保持现有 Rust 所有权和无环依赖。领域层承担可序列化契约和纯判定，配置层承担验证与规划，
  应用层编排，适配器规范化外部证据，runner 有界执行，接口层呈现结果。
  环境、路径和网络操作仍由各自 owner 管理；阻塞工作不进入异步编排主路径。
- 进程输出、文件大小、并发和时间仍需有界。快照摘要与输入保护不等于操作系统沙箱或完全可复现环境；
  外部执行环境与凭据隔离由调用方负责。来源文本和模型建议不得未经验证直接成为可执行配置。
- 完整 Agent 编排、模型路由、通用记忆、内置模型评审服务和大规模规则扩张列为暂缓方向。
  外部结果交换和缓存仅在试点证明需求后扩展；缓存必须满足已有输入一致性约束。

## 4. 演进需求

### EVO-01 按任务类型组织验收

**问题与基础**：编译和 lint 通过不足以证明需求完成，统一要求旧代码反例也会误拦截合法重构。
现有[任务契约](../../docs/en/02-reference/04-policy-task-and-signed-evidence.md)、[测试有效性](../../docs/en/02-reference/02-rules.md)
与[接口兼容性](../../docs/en/02-reference/03-projects-and-tool-reports.md)提供可复用机制。

**优先级**：P0，先验证缺陷修复和重构模板；其余模板随任务样本验证扩展。

| 子需求 | 增量要求 |
|---|---|
| EVO-01-01 | 提供有版本、适用前提、工具与报告要求、已知边界的任务模板。通过现有契约表达；选择和采用由调用方明确执行，不依据任务标题自动开启检查或豁免。 |
| EVO-01-02 | 缺陷修复模板描述原问题的可观察反例、修复后行为与相关回归。启用 `test_effectiveness` 时遵守现有独立测试文件、用例身份和允许断言类型契约。 |
| EVO-01-03 | 重构模板验证已声明行为保持、适用的接口兼容性和既有回归；新旧代码均通过是允许结果，不默认要求旧版本失败。 |
| EVO-01-04 | 新功能、性能、依赖升级及文档与规则修改按下表表达验收目标；缺乏生产者或可比较输入时披露能力缺口，不以通用成功退出替代所需证据。 |

| 任务类型 | 模板必须明确的验收内容 |
|---|---|
| 新功能 | 输入输出、边界条件、失败行为和适用的既有回归；新增 API 导致旧代码不能编译时，不把编译错误计为反例 |
| 性能优化 | 相同环境、负载、基准与测量方法下的成对观察，预先声明重复次数、阈值和波动处理，保留功能正确性检查 |
| 依赖升级 | 实际构建、适用的接口与运行行为，以及任务明确要求的安全检查；工具版本变化必须披露比较限制 |
| 文档与规则修改 | 内容、链接、示例和适用的规则正反例；验证配置或规则变更继续走既有策略审查流程 |

**验收与证据**：保留模板版本、采用后的契约摘要、实际命令与报告。
正例包括缺陷修复的有效反例和合法重构的双侧通过；负例包括缺失目标测试、旧代码编译错误、
测试身份变化、只验证新增行为却遗漏必需回归。反例只证明选定测试对具体旧实现有区分能力，
不能证明测试正确理解业务；关键行为还需独立案例、可信参考结果或人工复核。

### EVO-02 面向 Agent 的修复反馈

**问题与基础**：完整报告和日志可能占用大量上下文，Agent 还需区分修代码与补环境、补证据。
现有报告已提供稳定诊断标识、指纹、位置、证据、修复建议和固定策略的复验参数。

**优先级**：P0，先改善已有结果呈现，不引入模型调用。

| 子需求 | 增量要求 |
|---|---|
| EVO-02-01 | 提供从完整报告派生的有界精简反馈，分别呈现已确认违规、执行或能力缺口、尚未完成的交付检查。缺口不得伪装成已经确认的代码缺陷。 |
| EVO-02-02 | 保留运行、快照、策略和任务身份，关联验收项、诊断、证据引用与复验参数。未建立关联时明确未知，不能从文案推测业务映射。 |
| EVO-02-03 | 对重复诊断可归组，但保留成员身份和证据；明确省略数量、截断状态及完整报告位置。精简视图不能成为完整证据的替代品。 |
| EVO-02-04 | 复验指令继承已选基准、策略、任务与范围；展示局部复验和最终完整验收的差别。反馈不得默认要求关闭规则、降低级别或删除验收项。 |

**验收与证据**：完整和精简视图对同一报告必须给出一致的门禁与剩余交付项。
覆盖违规与超时同时存在、大量重复诊断、无任务关联、截断、证据不可用和原策略分支移动。
用实际输出规模与 Agent 使用记录测量反馈成本；字节数不冒充 token 数，未采集的 token 节省保持未知。

### EVO-03 跨 Agent 验收闭环

**问题与基础**：不同 Agent 对退出码和完成条件的理解可能不同，分支分别通过也不能证明组合结果通过。
现有 Skill、CLI、[任务计划](../../docs/en/02-reference/04-policy-task-and-signed-evidence.md)与快照一致性机制提供共同基础。

**优先级**：P0，至少两种实际使用的 Agent，优先同一项目中的缺陷修复与重构。
2026-09-15 用户限定本地仅使用 Codex：阶段 A/B 本地接入采用同一 Codex 的中、低能力模型配置组模拟两种 Agent。
固定相同推理强度、提示词、工具权限和预算，独立会话与工作副本；这项对照只验证跨模型接入，
不能据此关闭跨产品 Agent 的兼容性与实际修复验收。

| 子需求 | 增量要求 |
|---|---|
| EVO-03-01 | 提供薄接入范例和契约回归：通过 Skill、hook 或 CI 调用相同 CLI，不复制门禁计算。Agent 产品和版本属于运行记录，不硬编码进质量策略。 |
| EVO-03-02 | 实际运行必须验证 Agent 正确解释 `0/1/2`，按有效诊断修复，并保留原任务和策略。退出码 2 应报告未完成原因，不能通过无条件重试或吞掉状态宣称成功。 |
| EVO-03-03 | 外层 harness 管理重试、资源预算和无进展终止；保存初始报告、每次改动、复验结果和终止原因。中断或预算耗尽保留未完成状态。 |
| EVO-03-04 | 最终完整验收绑定实际提交、暂存区或工作区快照；多 Agent 组合或合并后的结果必须重新验证，任一代码或验证输入变动都不能沿用失配报告。 |

**验收与证据**：同一契约的受控接入测试覆盖通过、违规、未完成、策略修改和局部检查。
真实试点分别保留两种 Agent 的执行记录、预算、修复次数与最终完整报告。
增加“两个分支分别通过、合并后回归”的反例。Rust 临时仓库测试可以验证接入契约，
但固定脚本修复和 fixture 结果不能计为真实 Agent 自主修复收益。

### EVO-04 从失败案例演进规则

**问题与基础**：新增规则可能重复已有检查、过拟合个案或误拦截正常实现。
复用已有[策略演进](../../docs/en/02-reference/04-policy-task-and-signed-evidence.md)与[受保护验证](../../docs/en/02-reference/04-policy-task-and-signed-evidence.md)，
增量重点是失败案例质量、独立验证和后续收益，避免重新建设审批与存储机制。

**优先级**：P1，P0 采集可复查失败后推进。

| 子需求 | 增量要求 |
|---|---|
| EVO-04-01 | Agent 可由问题、审查意见或能力缺口提出规则和测试候选；候选必须关联原始案例、来源摘要、适用范围、预期拦截与正常通过行为。提案和案例标签不自动成为可信事实。 |
| EVO-04-02 | 区分生成案例、人工确认案例与未参与生成或调参的独立验证案例，记录来源和复核者。已被用于调参的案例必须重新分类，不能继续声明为独立验证。 |
| EVO-04-03 | 在可比较的任务、快照、工具、环境与预算下验证当前策略和候选策略，保留正例误拦截、漏检与执行未完成。不能仅凭候选通过其生成样例批准推广。 |
| EVO-04-04 | 沿用独立批准、不可变版本、推广和回退流程。跟踪采用后效果；误报或无增量收益的规则可提出降级、退役或重新验证候选，保留历史证据且不自动降低有效策略。 |

**验收与证据**：复用已有拒绝自批准、过期或撤销记录、受保护输入变化、候选回归和回退测试。
新增案例来源与独立性场景：生成案例全部通过但独立正常案例被阻塞、训练样例被误标为独立案例、
候选只减少告警却遗漏已确认问题。模型或多模型一致意见不替代受信批准与独立验收。

### EVO-05 真实收益与交付成本评估

**问题与基础**：现有 fixture 和 CI 不能证明审查时间节省，已有分析器的发现也不能重复归因。
复用[试点协议](../../docs/en/01-user-guide/05-real-repository-pilot.md)的样本、诊断归因、修复预算与人工复核要求。

**优先级**：P0 定义并采集记录；P1 根据真实样本完善结构化汇总。

| 子需求 | 增量要求 |
|---|---|
| EVO-05-01 | 试点启动前固定项目、任务类型、抽样方法、Agent、环境、预算、观察周期、样本量、复核比例和各项数值接受阈值；缺少这些输入时保持试点未启动或未完成。 |
| EVO-05-02 | 保留同一输入上的既有工具基线，分别标记原工具发现、qualitygate 新增规则发现和证据完整性拦截；用独立问题身份去重，并分别汇总历史回放、故障注入和日常开发。 |
| EVO-05-03 | 按下表记录指标、分子分母、样本和排除理由。保留所有失败、超时、放弃与未完成尝试；数据缺失或零分母使用未知及原因，不补零或只保留成功样本。 |
| EVO-05-04 | 记录 Agent/harness 版本、请求模型标识、服务商可提供的实际模型或版本信息及采集时间；无法确认实际版本时明确未知。工具、环境、预算和缓存条件不可比较的样本分别分组，不作因果收益结论。 |

| 指标 | 口径与边界 |
|---|---|
| 独立问题与检测率 | 人工确认并去重的问题数；仅当存在预先建立的独立问题集时计算检测率，未知漏检不能计为零 |
| 误报率 | 人工判定误报数 / 已复核诊断数，同时记录未复核量；告警减少不能直接解释为误报减少 |
| 修复成功率 | 约定预算内修复且完整复验通过的有效可修复案例 / 全部已分配的有效可修复案例，保留未完成案例 |
| 成功与稳定性 | 分开记录首次成功、限定次数内至少一次成功、重复运行全部成功；明确尝试次数，不用最佳一次代表稳定性 |
| 审查负担 | 可比任务的人工活跃分钟、相关意见数和返工轮次；记录复核规则与样本差异 |
| 检查成本与完成率 | quick/full 耗时分布、样本数、工具和缓存条件；已完成必需检查 / 预期必需检查，单列不适用及未完成原因 |
| 每个合格交付成本 | 同一观察组全部尝试的成本 / 完整通过任务验收的任务数；失败尝试计入分子，零合格交付时结果未知 |

人工分钟、用量与可得的模型/基础设施费用分别记录。汇总金额时必须提供币种、计价时间、转换方法和成本覆盖范围；
缺少成本来源时只能报告已测部分，不能宣称完整总成本，v10 的非财务验收不因而失效。完整通过仅指既定契约和验证边界，
不能据此证明线上无缺陷。上线后缺陷收益需要另行采集真实观察。

**验收与证据**：公开可复查的样本清单、计算口径、聚合结果与来源引用，私有内容可留在团队证据库。
覆盖重复诊断、未复核诊断、成本缺失、零分母、模型版本未知、失败尝试遗漏和不同环境错误合并。
只有满足预先确定阈值并保留授权验收记录后，才把该试点标为通过。

以下是试点启动前必须由团队确定的输入，本 SPEC 不预填未经确认的选择：

- 项目 URL 或本地来源、不可变基准、试点负责人、受信策略与任务契约。
- Agent 产品及版本、模型采集方式、允许的任务类型、采样及比较方法；本地阶段 A/B 按上述用户约束
  使用 Codex 两种模型，后续跨产品验收仍需至少两种实际产品。
- 工具与环境、quick/full 范围、重试和资源预算、无进展终止与排除规则。
- 样本量、观察周期、最小人工复核比例，以及检测、误报、修复、审查负担、完成率和耗时的数字阈值；金额阈值只适用于旧版计价计划。
- 证据保留位置、隐私处理、复核责任人与试点验收记录。

2026-09-16 用户已确认本轮试点使用 qualitygate-cli、8 个任务（缺陷修复和重构各 4 个）、

阶段 D 的工程命令 `pilot seal --input` 在 observation 为空时计算计划摘要。封存要求 real 来源、
预先声明的 expected issues、无事后 exclusion、至少两个请求模型组、existing-tools/qualitygate
两种流程及每个 input 相同的完整 cohort 矩阵。摘要绑定协议和 assignment，但有意允许执行后补充
服务商实际模型标识和 observation。摘要只能检测内容变化，不能认证封存人或可信时间；首次输出
仍须进入团队持久归档。细化要求与证据见[阶段 D 设计](../design/pilot-phase-d.md)和
[阶段 D 记录](../../docs/en/01-user-guide/05-real-repository-pilot.md)。

阶段 E 的 `pilot authorization-subject --input` 从封存清单导出唯一启动主题；外部 human owner
使用具备 `pilot-plan-authorization` scope 的 Ed25519 key 签署 DSSE record。`pilot summarize`
在每次调用时重验外部 trust store、仓库、owner key、精确主题、签发/到期窗口和撤销状态，输出
authenticated 或 absent。签名输入必须位于被测仓库外，不能由仓库提交自授权。普通数字签名仍不
提供独立可信时间，启动授权也不是最终 reviewer 接受。细化要求与证据见
[阶段 E 设计](../design/pilot-phase-e.md)和[阶段 E 记录](../../docs/en/01-user-guide/05-real-repository-pilot.md)。

阶段 F 的 `pilot acceptance-subject` 只为完整、protocol-ready 的观察生成最终主题。评估聚合
Qualitygate 组的检测、误报、修复、完成与复核比例，并要求每个匹配对照的 inventory、审查时间、
full P95 和成本比通过；失败与 unknown 均不能签成 accepted。外部独立 reviewer 使用
`pilot-trial-acceptance` scope 签署接受或拒绝，`pilot summarize --acceptance` 每次重验主题、
身份、有效期和撤销。细化要求与证据见[阶段 F 设计](../design/pilot-phase-f.md)和
[阶段 F 记录](../../docs/en/01-user-guide/05-real-repository-pilot.md)。

阶段 G 的 schema v2 在封存前要求结构化总预算。纯计算包含两流程、两模型的全部尝试及按

第十项总预算检查，旧 v1 已封存记录维持九项语义。细化要求与证据见
[阶段 G 设计](../design/pilot-phase-g.md)和[阶段 G 记录](../../docs/en/01-user-guide/05-real-repository-pilot.md)。

阶段 H 的 schema v3 在封存前要求 `task_mix` 配额总和等于任务总数，并按不同输入 ID
核对任务类型；不同输入不得复用任务 ID 或契约摘要。摘要绑定配额与任务身份，汇总列出
去重任务清单。v3 沿用 v2 预算和十项最终阈值，旧 v1/v2 已封存记录维持原语义。

阶段 I 的 schema v4 在封存前要求每项独立任务有一份有界来源工件，声明 issue/commit
身份、相对路径、字节数、SHA-256 和选入时间。CLI 每次封存、导出签名主题或汇总时
重新核对文件；来源字段进入 plan seal 与汇总审计。旧 v1/v2/v3 已封存记录保持原语义。
摘要匹配不证明来源内容与时间真实，正式样本仍须外部复核。
细化要求与证据见[阶段 I 设计](../design/pilot-phase-i.md)和
[阶段 I 记录](../../docs/en/01-user-guide/05-real-repository-pilot.md)。

阶段 J 的 schema v5 在封存前要求 `run_order` 恰好排列全部 assignment，按相邻流程
交替，并在每个任务类型×请求模型层内平衡两流程谁先执行。观察的 `start_sequence`
声明实际启动次序；缺失或偏离进入汇总的 `schedule_audit` 和协议限制。旧 v1–v4
封存摘要维持原语义。序号本身不是可信时钟，须对照外部日志人工核对。
细化要求与证据见[阶段 J 设计](../design/pilot-phase-j.md)和
[阶段 J 记录](../../docs/en/01-user-guide/05-real-repository-pilot.md)。

阶段 K 的 schema v6 要求每个 assignment 在观察前有一份可核对的初始完整报告，
并封存 `no_progress_limit`。CLI 用与阶段 B harness 相同的错误诊断/阻塞项真子集规则
重算进展；超预算或连续两次无进展后再试进入 `attempt_audit` 协议偏离。失败尝试
仍保留在分母和成本，初始报告文件缺失/漂移为未完成。旧 v1–v5 封存摘要保持原语义。
细化要求与证据见[阶段 K 设计](../design/pilot-phase-k.md)和
[阶段 K 记录](../../docs/en/01-user-guide/05-real-repository-pilot.md)。

阶段 L 的 schema v7 在每个观察中绑定请求模型、Agent/harness 身份、采集时间和
报告的实际模型或明确未知原因。CLI 有界复核外部归档 JSON，缺失或失配保持未完成；
明确未知不再单独阻断协议，比较结论仅针对请求配置。旧 v1–v6 语义保持不变。
细化要求与证据见[阶段 L 设计](../design/pilot-phase-l.md)和
[阶段 L 记录](../../docs/en/01-user-guide/05-real-repository-pilot.md)。

阶段 M 的 schema v8 将模型证据定位到每个尝试，包括失败、超时和放弃的尝试。

明确未知不冒充报告的身份。运行单元级 v7 记录在 v8 禁用；旧 v1–v7 语义不变。
细化要求与证据见[阶段 M 设计](../design/pilot-phase-m.md)和
[阶段 M 记录](../../docs/en/01-user-guide/05-real-repository-pilot.md)。

阶段 N 的 schema v9 为每次尝试增加归档执行记录，核对开始/结束毫秒与

缺记录保留为未完成，逆序阻止最终接受；记录与清单冲突或归档文件漂移
拒绝输出。旧 v1–v8 保持原语义，时间真实性仍需 reviewer 对照原始日志。

### 6.1 必须保留的反例

| 场景 | 预期行为 | 关联需求 |
|---|---|---|
| 零测试、缺报告、超时、未知生产者结果 | 保留证据缺口，不能通过；并发存在的违规仍可见 | EVO-02、EVO-03 |
| 删除验收项、修改规则或受保护验证资产 | 原受信要求仍有效，未经授权不能使交付通过 | EVO-01、EVO-03、EVO-04 |
| staged 与 worktree 不同、执行期间输入变化或报告过期 | 按实际选择验证，失配结果不能复用 | EVO-03 |
| 旧代码编译失败、断言类型未知、测试身份变化 | 不计为有效反例；按现有测试有效性契约报告未完成 | EVO-01 |
| 合法重构在新旧实现均通过 | 不因缺少旧代码失败而阻塞；继续满足已选回归和兼容性要求 | EVO-01 |
| 局部检查通过但存在未执行必需项 | 显示剩余交付检查，不能宣称任务完成 | EVO-02、EVO-03 |
| 分支分别通过，组合后引入回归 | 最终组合快照验收发现回归，旧分支报告不能授权交付 | EVO-03 |
| 候选通过生成样例但误拦截独立正常案例 | 保留候选回归，不允许以生成样例通过代替推广证据 | EVO-04 |
| 重复告警、成本缺失、全组失败或不同比较条件 | 去重、未知与分组口径正确，失败不从分母或成本中消失 | EVO-05 |

### 6.2 文档、实现与收益分别验收

- 文档验收检查需求编号、链接、状态和研究来源，运行 `cargo test --locked --test quality documentation`、
  `relay-knowledge map validate --format json`，保持 authored 文件不超过 1000 行。
- 实现验收按 [Rust 质量契约](../../docs/en/04-contributor-guide/01-development-and-quality-gates.md)运行格式、编译、Clippy、所有目标与特性测试及至少 90% 行覆盖率；
  单元与集成证据分开，临时 Git 仓库隔离，Miri 与 ASan 保持独立。owner 或依赖变化需运行架构门禁。
- 新行为必须有独立正反例与需求到测试映射。必需工具不可用、未执行的 live producer 或受限平台不能冒充已验证。
- 真实 Agent 表现和团队收益按 EVO-05 单独验收。本文档、受控回归与内部自检通过均不改变试点的待验收状态。

## 7. 剩余验收与收尾边界

阶段 O 完成用户明确的非财务契约调整。剩余工作是按已确认的 8 项任务、7 天协议
采集真实证据并完成独立决策，不继续用 fixture 代替试点。
[收尾设计](../design/pilot-closeout.md)列出依赖顺序，
[当前准备度审计](../../docs/en/01-user-guide/05-real-repository-pilot.md)记录已具备和缺失的输入。

当前本地仅获准使用同一 Codex 的 Terra/Luna 两组；这可验证跨模型对照，
不能满足 EVO-03 对至少两种实际 Agent 产品的跨产品目标。真实试点也尚缺
独立任务清单与真值、human owner 和 reviewer、仓库外持久归档、
封存的策略/任务契约、32 份初始报告及启动授权。缺任一先决输入时不得把
候选计划标为已封存、把历史回放标为 real，或启动七天收益观察。七天后的
验收还需全部尝试、人工复核、原始模型/时钟记录、完整检查和 reviewer 签名。
