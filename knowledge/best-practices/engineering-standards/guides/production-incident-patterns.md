# 从现网事故提取可验证的编程约束

核对日期为 2026-11-18。以下十六份运营方一手资料记录了故障发生的条件，三项实证研究帮助选取测试场景，三项本仓库修复展示了门禁本身也会判错。样本按故障机制选取，用于提出约束和回归用例。各项在当前项目里的实现状态、工具接入方式和验收条件见[现网事故防护规格](../../../../codespec/requirements/production-incident-guards.md)。

## 优先检查的异常终止、泄漏和越界

### IG-13 · Cloudflare NGINX · 进程异常终止和 core dump

Cloudflare 调查线上 NGINX 工作进程的异常终止时，从 core dump 区分出了多项软件缺陷。另有一批无法从代码解释的崩溃集中在特定 CPU 型号，更新微码后这批崩溃消失。信号描述进程怎样终止；栈、构建版本和环境帮助判断原因。[Cloudflare 工程调查](https://blog.cloudflare.com/however-improbable-the-story-of-a-processor-bug/)

建议让测试执行器保留异常终止的进程角色、退出状态或信号，以及已完成的用例数。受测程序异常退出且独立执行器完整记录了失败用例，可形成测试违规；执行器自身崩溃、未交付可信结果，属于执行不完整。系统可关闭转储或把它交给外部服务处理，因此应能用退出证据识别异常终止。需要关联转储时只记录受控位置和身份，避免把包含进程内存的整份文件嵌进报告。

### IG-14 · Shopify · 依赖出错时原生扩展泄漏堆内存

Shopify 的应用服务器在压力下持续消耗内存，出现 `ENOMEM`。团队观察到 memcached 不可用时，继续写缓存会累积内存占用，最终定位到客户端库的 C 扩展。更换并随后修复该库解决了线上问题。此前对 Ruby 堆中存活对象的单次采样没有定位到原因。[Shopify 工程调查](https://shopify.engineering/17488512-most-memory-leaks-are-good)

建议在一次进程生命周期内重复“依赖成功、失败、恢复”，在相同的预热和回收条件下比较已分配而未释放的字节和对象数。原生分配可用 LeakSanitizer 等工具检查；对象仍可达、实际已无业务用途时，还需用堆快照追踪保留路径。RSS 上升会受缓存、分配器和共享页影响，只适合作为调查信号。未启用泄漏检测或提前退出的用例应报告证据缺失。

### IG-15 · Cloudflare · 连接未关闭，资源泄漏

Cloudflare 跟踪到一个监听程序没有关闭部分套接字，连接长期停留在 `CLOSE_WAIT`。即使远未用完进程的文件描述符，旧连接状态也已导致一些新的本地连接超时。因此，仅监测“是否达到句柄上限”会错过功能影响。[Cloudflare 工程调查](https://blog.cloudflare.com/this-is-strictly-a-violation-of-the-tcp-specification/)

建议按资源种类对文件、套接字、子进程等分别记账，在成功、提前返回、取消和超时后等候清理完成，比较占用和预热后的稳定基线。对连接池等有意保留的资源要记录允许的容量与归还条件。内存检测器没有发现堆泄漏，不能回答这些资源是否已释放。

### IG-16 · CrowdStrike Windows 传感器，2024-07-19 · 跨组件字段数不一致导致越界

模板校验与实际提供给解释器的字段数相差一项。早期测试与部署都未读取到这个缺失字段，后续内容更新首次用到它时发生越界读取，导致 Windows 系统崩溃。[CrowdStrike 根因报告](https://www.crowdstrike.com/wp-content/uploads/2024/08/Channel-File-291-Incident-Root-Cause-Analysis-08.06.2024.pdf)

建议在隔离的项目测试中让生产者、校验器和消费者走同一入口，覆盖空输入、最后一个有效位置、首个无效位置、截断及长度不一致。可用原生 ASan 或适用的 Miri 测试补充内存访问证据；安全 Rust 的索引越界也可能表现为 panic，应同时断言对无效输入返回预期错误。任何结论都要附上实际运行的平台、组件和输入范围。

## 现网事故

### IG-01 · AWS DynamoDB，2025-10-19 至 20 · 过期写入与清理并发

美国北弗吉尼亚区域的 DNS 执行器在开始应用计划前校验一次版本。一个执行器因重试而变慢，在另一个执行器提交新版后又写回了旧版。并发清理删除了重新生效的旧计划，区域端点地址被清空，自动化也无法继续更新。[AWS 复盘](https://aws.amazon.com/message/101925/)

建议对“提交”和“清理”设置可控调度点，分别验证已发布版本只能前进、活动计划的记录仍可读取。在模型中保留失败时的操作顺序，以便复查。模型结论限于纳入测试的状态、事务边界和交错顺序。

### IG-02 · Google Cloud Service Control，2025-06-12 · 数据变更激活潜伏分支

新配额检查随二进制逐区域发布，期间没有策略数据触发该分支。随后含空字段的策略迅速复制到各区域，新分支解引用空指针并造成循环崩溃。恢复时，部分区域的大批实例同时重启，又给依赖服务带来过高负载。[Google Cloud 复盘](https://status.cloud.google.com/incidents/ow5i3PPK96RduMcb1SsW)

建议从真实策略加载入口传入旧版、字段缺失和空值样本，用断言确认新分支实际执行，检查错误路径是否返回约定的决策。跨区域启用节奏和重启流量还需发布平台、负载演练提供证据。

### IG-03 · Azure Front Door，2025-10-29 · 异步处理晚于发布晋级

跨两个控制面版本执行的合法变更生成了不兼容元数据。边缘数据面接收配置后约五分钟才在异步处理中崩溃。此前各阶段已上报健康，配置传播至多数边缘节点，也进入了用来回退的最近可用快照。[Azure 复盘 YKYN-BWZ](https://azure.status.microsoft/en-us/status/history/?trackingId=YKYN-BWZ)

建议用相邻版本按顺序写入并消费同一配置，覆盖异步任务的完成和失败。测试失败时应能确认候选配置没有晋级、原快照可以恢复。生产环境的观察时长和健康信号是否涵盖实际消费路径，需要部署记录佐证。

### IG-04 · Cloudflare，2025-11-18 · 生成数据突破消费者上限

数据库权限调整扩大了查询可见范围。生成特征配置的查询按表名取字段，跨库返回了重复行。超量特征触及消费者上限，新版 FL2 代理对错误结果调用 Rust 的 `unwrap`，使依赖该模块的请求返回 5xx。旧版代理的表现不同，错误体现在机器人评分上。[Cloudflare 复盘](https://blog.cloudflare.com/18-november-2025-outage/)

建议给同名跨库数据、重复字段、恰达上限和超过一个元素的产物各设用例。断言生成记录的范围和唯一性，并让受支持的消费者实际读取产物。静态规则可定位指定生产模块中未处理的取值操作；产物基数与错误后的服务行为由契约测试检验。

### IG-05 · 阿里云香港可用区 C，2022-12-18 · 恢复路径共享故障域

机房制冷故障使多个服务下线。ECS 控制面原本在 B、C 区双活，但 B 区扩容所需的中间件位于 C 区；另有部分自定义镜像只存放在 C 区的本地冗余 OSS 中。其他区的客户即使成功购买实例，仍可能无法启动。[阿里云复盘](https://www.alibabacloud.com/zh/notice/resolved_service_outage_in_zone_c_of_the_china_hong_kong_region_1ae?_p_lc=1)

建议在有部署清单的项目中沿“扩容 → 中间件”和“启动 → 镜像”检查传递依赖所属的故障域，并要求一项独立的单区不可用演练跑通这两条恢复路径。清单检查的结论限于已声明的依赖；制冷设施、剩余容量和实际可切换性由运行团队验证。

### IG-06 · Cloudflare DNS，2016 年末闰秒 · 墙钟回拨影响耗时计算

DNS 解析器用墙钟差计算上游响应时间。闰秒时钟回拨产生负耗时，多次采样后，平滑值也变为负数。上游选择函数接收到负参数时发生 panic，部分 DNS 查询失败。[Cloudflare 复盘](https://blog.cloudflare.com/how-and-why-the-leap-second-affected-cloudflare-dns/)

建议在耗时测量入口注入时钟，让墙钟倒退而单调时钟继续前进，验证下游选择可以完成、耗时满足非负约束。若用静态检查，限定于超时、重试和耗时计算；审计日志或证据时间戳本身有记录日历时间的需要。

### IG-07 · AWS S3，2017-02-28 · 合法操作移除了过多容量

授权操作人员按既有手册维护服务时录错命令参数，实际移除的服务器远多于预期，连带影响索引和放置子系统。AWS 随后降低移除容量的速率，并加入子系统最低容量保护。[AWS S3 复盘](https://aws.amazon.com/message/41926/)

建议给批量操作的规划函数输入一组模拟库存，让不同批次的累计移除量恰达和超过子系统容量下限，验证越界计划在执行前被拒绝。真实容量的获取、新旧计划并发和现场限速仍需操作平台保证。

## 历史研究

**IG-08 · 错误处理缺口。** Yuan 等人分析了 Cassandra、HBase、HDFS、Hadoop MapReduce 和 Redis 中随机选取的 198 个用户报告故障。作者发现，样本中许多严重故障源于错误处理代码，多个事件的顺序也会影响故障能否触发。可据此给本项目的依赖调用设计对照测试：正常输入产生预期结果，依赖超时或报告不完整时保留已有证据，并中止依赖该结果的检查。论文的统计量只描述其研究样本。[OSDI 2014 论文](https://www.usenix.org/conference/osdi14/technical-sessions/presentation/yuan)

**IG-09 · 跨变量状态与执行次序。** Lu 等人分析了 MySQL、Apache、Mozilla 和 OpenOffice 中的 105 个并发缺陷。在所研究的非死锁缺陷中，约三分之一违反操作间的先后约束，另有约三分之一涉及多个变量。测试可将“发布后方可读取”“读者仍使用时应保留对象”写成可观测断言，以受控调度覆盖关键交错。某一次压力测试无异常，只能说明该次观察到的执行结果。[ASPLOS 2008 论文](https://pages.cs.wisc.edu/~shanlu/paper/asplos122-lu.pdf)

## IG-17 · 模块循环依赖的项目证据

循环依赖取决于构图的节点。两个业务模块可能共用一个顶层 owner，在 owner 图中看不到这两个模块之间的边；同样，两个模块共用下游也不会自然构成环。本项目的生产 Rust 图检验顶层 owner 契约。语法解析后的直接环、三方环和共享下游对照见[架构实验](../../../../codespec/test/production-incident-regressions.md)。独立的 Java 实验用编译器检查具名模块的 requires 边，并保留环涉及的模块名和诊断位置。[模块编译实验](../../../../codespec/test/production-incident-models.md)

## 任务积压、线程预算与重试

### IG-18 · 未结束的工作长期保留内存

WarpStream 发现线上控制面的 Go 堆用量缓慢增长。在预发布环境采集 core 并沿引用链定位，发现任务队列已满时，清理扫描器的重试循环一直未检查工作单元发出的取消信号。存活的 goroutine 仍持有共享队列及在途任务的数据。队列入口开始检查取消后，生产堆指标停止持续线性增长。[WarpStream 工程调查，2025-04-02](https://www.warpstream.com/blog/a-trip-down-memory-lane-how-we-resolved-a-memory-leak-when-pprof-failed-us)

Huang 等人研究了 Twitter 的一次线上峰值测试。积压增加了垃圾回收负担，处理速度下降又加深积压。论文用 Little 定律估计线上平均在途请求数，并在受控实验中直接测量队列，验证了反馈回路。BigQuery 在 2022-05-24 至 25 的事故提供了另一种暴露条件。内存泄漏随审计日志路径的执行逐渐累积，经足量流量和时间后，部分节点无法接收新作业。Google 的复盘未披露泄漏对象是否仍可达。[OSDI 2022 论文第 4、5 节](https://www.usenix.org/conference/osdi22/presentation/huang-lexiang) · [BigQuery 复盘](https://status.cloud.google.com/incidents/Gt6njQyniuxXViQULV2T)

用有界模型反复提交、完成、取消和超时，观察工作项数、保留负载字节及停止接收后能否排空。负载与期限可由测试控制，使回归检查不依赖机器速度。要评价真实内存压力，需足量重复执行生产入口，在固定预热与采样条件下记录活跃对象、持有路径或驻留资源。不可达堆泄漏检测只能覆盖其插桩和实际执行的路径。

### IG-19 · AWS Kinesis，2020-11-25 · 扩容耗尽每台前端的线程预算

Kinesis 每台前端为同一集群中的其他前端创建操作系统线程。小幅扩容使既有节点也增加线程，触及操作系统配置上限。前端未能完成分片映射缓存的构建，因而无法正确路由请求。恢复时，重建缓存还和处理流量争用资源，团队只能逐步恢复前端。[AWS Kinesis 复盘](https://aws.amazon.com/message/11201/)

用已声明的拓扑、运行时线程上限和启动预留量测试扩容边界。检查器应计算单节点与全局的线程需求，在分配前拒绝超界计划，并验证部分创建失败后的清理及重试。部署环境还要核实实际线程、PID 或容器限制、扩容拓扑和初始化阶段的资源峰值。

### IG-20 · Azure AI 服务 · 错误分类、连接占用与多层重试放大

2026-05-29，上游改动将部分容量耗尽反馈以暂时性服务器错误向上传递，多层调用者随即反复重试。Azure 观察到单次失败有时会引出最多 48 次额外尝试，共享路由层耗尽资源，部分实例 OOM。2026-09-29 的另一起事故中，发布清空缓存，读缓存缺陷又放大回源流量。依赖延迟拉长连接占用时间，叠加重试耗尽出站连接容量。依赖数据库连通性的健康检查随后引发重启循环。[Azure 复盘 LYXT-C1Z](https://azure.status.microsoft/en-us/status/history/?trackingId=LYXT-C1Z) · [Azure 复盘 7QL5-Z50](https://azure.status.microsoft/en-us/status/history/?trackingId=7QL5-Z50)

对同一逻辑请求分别注入容量拒绝、暂时失败和期限耗尽，断言错误分类、跨层共享的尝试总数与截止时间。独立的连接实验应延迟依赖响应并观察峰值在途连接数，在取消或超时后复查连接归还和服务恢复。重试预算的模型覆盖指定调用路径，真实连接容量、健康探测和跨区域退避需实际拓扑与遥测。

## 后续案例的收录与复查

1. 记录事故日期、来源链接、报告版本或跟踪 ID，以及已确认的触发条件、失效链和影响。实证论文注明样本及度量方式。工程推导放在独立段落，标明类比所用的假设。
2. 将相同失效机制的新案例附到原有 IG 编号，首次出现的机制使用新编号。同步更新规格和证据索引，使报告、约束与复现命令可以互查。
3. 执行可复查的一组对照。确认缺陷版产生预期违规、正常版通过、必需证据缺失时保留不完整状态。记录快照、规则或工具版本、样本、命令、报告范围和退出结果。没有可测判据时，保留当前覆盖缺口及所需的运行环境证据。
